# firewall-detection
# 基于 YOLO、可切换时序门控与 MViT-v2-S 的两级火灾烟雾检测系统设计方案

## 1. 文档目的

本文档描述当前项目的完整火灾与烟雾视频检测方案。系统采用两级级联架构：第一级使用已经训练完成的 YOLO 模型持续发现 `fire` 和 `smoke` 候选；候选经过目标跟踪以及 TPT 或 AVT 时序门控后，第二级使用 MViT-v2-S 视频 Transformer、时间频域特征和轨迹统计特征进行真实性验证；最后通过多窗口投票、会话重关联和报警冷却生成稳定报警。

系统不让任何一个模型独立承担全部任务，而是将职责拆分为：

- **YOLO 候选检测器**：强调召回率，快速定位疑似火焰或烟雾；
- **目标跟踪器**：把离散检测框组织为同一摄像头、同一类别、同一目标的轨迹；
- **TPT/AVT 时序门控**：过滤瞬时误检并控制第二级模型调用频率，两种算法可按场景切换；
- **MViT-v2-S 视频验证器**：同时从外观时序、时间频率和轨迹变化三个角度判断候选是否真实；
- **多窗口投票与事件管理器**：抑制单窗口抖动、轨迹碎片导致的重复任务和重复报警；
- **日志与报警接口**：输出可追踪、可复现的验证与报警记录。

本文档基于当前仓库已经完成的实现和实验结果重写。文中会明确区分：

1. 已经在代码中实现并可直接运行的功能；
2. 在现有 49 个视频上得到的域内实验结果；
3. 正式部署前仍需通过独立数据完成的验证工作。

## 2. 设计目标与基本原则

### 2.1 设计目标

系统需要同时满足以下目标：

- 在正常监控阶段保持较低计算开销；
- 尽量保留 YOLO 对早期、小目标火焰和烟雾的召回率；
- 过滤单帧高亮、反光、蒸汽、云雾、灯光等瞬时误报；
- 利用连续视频的外观变化和频率变化进行二次判断；
- 即使检测框短时丢失或轨迹 ID 改变，也能维持同一验证事件；
- 对同一火灾过程只产生必要的报警，不因轨迹碎片反复报警；
- 保留模型版本、阈值、片段质量、推理耗时和事件 ID，便于工程审计。

### 2.2 级联系统原则

两级系统的核心原则是：

```text
第一级负责“发现可能发生了什么”
时序门控负责“是否值得进一步验证”
第二级负责“候选是否真实”
事件管理负责“是否应该形成一次报警”
```

YOLO 的单帧结果不能直接作为最终报警，大模型的单个窗口结果也不能直接作为最终报警。最终报警必须同时经过候选检测、时序门控、视频验证和多窗口投票。

### 2.3 当前实现边界

当前仓库已经完成：

- Ultralytics YOLO 视频推理；
- 分类目标跟踪；
- TPT 与 AVT 两种门控算法及配置切换；
- 3.2 秒视频环形缓冲和轨迹 ROI 构建；
- MViT-v2-S、rFFT、轨迹统计三分支融合模型；
- 两阶段训练、阈值校准、片段级和事件级评估；
- 在线 2/3 窗口投票；
- 轨迹失配宽限、验证会话重关联和报警冷却；
- 候选采集、JSONL 事件日志和故障输出。

当前报警输出为程序事件和 JSONL 日志。真实项目中的短信、平台消息、声光报警器、视频归档和人工确认接口，需要在现有 `alarm` 事件之上继续接入。

## 4. 第一级：YOLO 候选检测

### 4.1 模型定位

当前使用的模型权重为：

```text
yolo26s-p2-1024-recall/weights/best.pt
```

默认输入尺寸为 `1024`。该模型已经能够输出 `fire` 和 `smoke` 检测框，因此本方案不改变 YOLO 的类别定义，而把它作为高召回候选生成器。

典型输出结构为：

```python
detection = {
    "camera_id": "camera_001",
    "timestamp": 1712345678.123,
    "class_name": "fire",       # fire 或 smoke
    "confidence": 0.72,
    "bbox": [x1, y1, x2, y2],
}
```

### 4.2 两层置信度策略

在线推理时，`model.predict()` 使用较低的 `conf=0.01` 保留原始候选，再由后处理按类别过滤：

```yaml
candidate_confidence:
  fire: 0.60
  smoke: 0.20
default_candidate_confidence: 0.25
```

这样做的原因是火焰和烟雾的置信度分布不同。烟雾形态松散、边界弱，如果直接使用与火焰相同的高阈值，容易在进入时序模块前被删除。当前 49 个视频的组合测试中，`fire=0.60`、`smoke=0.20` 与 AVT 的综合表现最好，因此已写入 `config/temporal.yaml`。

该结论只代表当前数据域中的最佳组合；换摄像头、分辨率或环境后必须重新校准。

### 4.3 是否需要额外 NMS

YOLO 后面需要非极大值抑制，但 Ultralytics 推理结果已经执行了模型自带 NMS。当前后处理接收的是 NMS 后的 `Results`，因此不再重复执行一次 NMS。

重复 NMS 可能产生两个问题：

- 相邻的多个真实火焰区域被错误合并或删除；
- 检测框数量和位置再次变化，反而加重轨迹 ID 抖动。

只有在以后改为直接读取模型原始 logits，或者发现特定类别仍大量输出重复框时，才应增加一次按类别 NMS，并单独验证 IoU 阈值。

### 4.4 忽略区域

对固定灯具、显示屏、炉口等长期误报区域，可以按摄像头和类别配置归一化忽略区。检测框中心落入匹配区域时，不进入跟踪器。

忽略区是工程规则，不应用来掩盖模型普遍性问题。每个忽略区都应记录设置原因，并保留定期复核机制。

## 5. 目标跟踪模块

### 5.1 跟踪目标

时序门控必须判断“同一个候选是否持续或变化”，不能只统计每帧是否存在任意检测框。跟踪状态按以下三级隔离：

```text
camera_id → class_name → track_id
```

每条轨迹保存：

```python
track = {
    "camera_id": "camera_001",
    "track_id": 12,
    "class_name": "smoke",
    "first_seen": 1712345670.0,
    "last_seen": 1712345673.0,
    "hit_count": 14,
    "miss_count": 2,
    "observations": [],          # bbox、置信度、时间戳、是否命中
}
```

### 5.2 关联方法

当前使用轻量级分类跟踪器，匹配依据包括：

- 检测框 IoU；
- 以目标尺寸归一化的中心点距离；
- 最近运动速度估计得到的短期预测框；
- 已稳定轨迹的连续性优先分数。

当前主要配置为：

```yaml
tracker:
  iou_threshold: 0.15
  center_distance_threshold: 1.5
  max_misses: 12
  max_missed_seconds: 1.5
  max_history: 64
  max_timestamp_gap: 5.0
  prediction_horizon_seconds: 0.75
```

如果 IoU 因火焰边界剧烈变化而降低，只要归一化中心距离仍合理，轨迹仍可继续；短期预测最多使用 0.75 秒，避免长时间外推产生错误关联。

### 5.3 轨迹碎片化问题与解决方案

火焰和烟雾不是刚性目标，检测框会扩张、收缩、漂移或短时消失。仅使用相邻帧 IoU 时，常见现象是一个真实目标不断获得新 `track_id`。这会导致：

```text
轨迹窗口不足 → 门控反复触发 → 验证窗口凑不满 2/3 → 重复验证或漏报警
```

当前系统从三个层面解决该问题：

1. **跟踪层**：使用短时运动预测、中心距离补充匹配，并允许最多 1.5 秒失配；
2. **验证会话层**：旧轨迹消失后保留最后 ROI 1.25 秒，新轨迹与旧 ROI 满足 `IoU≥0.05` 或归一化中心距离 `≤1.0` 时继承已有会话和投票；
3. **事件层**：同一空间区域及同一摄像头同类别均设置 10 秒冷却，碎片化产生的新门控事件不会立刻形成重复报警。

需要特别区分两个同名配置：

- `tracker.max_misses`：控制轨迹身份可以保持多久；
- `classes.*.max_misses`：只控制 TPT 窗口内允许多少次未命中。

二者含义不同，不能用修改 TPT 参数代替轨迹身份维护。

### 5.4 时间戳与断流

跟踪器使用真实时间戳而不仅是帧号。相邻推理时间差超过 `max_timestamp_gap=5.0` 秒时，系统重置该摄像头轨迹，避免断流前后的两段视频被错误拼成同一事件。

摄像头无帧、解码失败与“当前帧没有检测框”必须分开处理：前者属于采集故障，后者才是有效阴性观测。

## 6. 可切换的 TPT 与 AVT 门控

### 6.1 统一接口

TPT 和 AVT 位于同一跟踪器之后，输出统一的 `TriggerEvent`。可以通过命令行切换：

```bash
python run_temporal.py --source input.mp4 --temporal tpt
python run_temporal.py --source input.mp4 --temporal avt
```

也可以修改配置：

```yaml
temporal_mode: avt  # 可改为 tpt
```

命令行优先于 YAML。运行过程中切换算法时应重新创建后处理器，不能把上一种算法的内部窗口状态带入下一种算法。

### 6.2 TPT：时间持续性门控

TPT 回答的问题是：

> 同一轨迹是否在规定时间和采样窗口内持续出现，已经值得调用第二级模型？

基本条件为：

```python
should_verify = (
    hits_in_window >= min_hits
    and track_duration >= min_track_duration
    and max_confidence >= min_confidence
    and misses_in_window <= max_misses
)
```

当前按类别配置：

| 类别 | 窗口 | 最少命中 | 最短持续时间 | 最低置信度 | 高置信度快速通道 | 最大未命中 |
|---|---:|---:|---:|---:|---:|---:|
| fire | 3 | 2 | 1.0 s | 0.25 | 0.80 | 1 |
| smoke | 5 | 3 | 2.0 s | 0.25 | 0.85 | 2 |

火焰采用更短窗口以降低报警延迟；烟雾采用更长窗口，减少云雾和蒸汽造成的短时触发。高置信度候选可快速进入验证，但仍然只是调用大模型，不能绕过第二级直接报警。

### 6.3 AVT：面积变化门控

AVT 参考 `pedbrgs/Fire-Detection` 项目的面积变化思想。它不要求目标框尺寸稳定，而是利用火焰和烟雾边界变化明显这一特点，计算最近有效检测框面积的变异系数：

```text
CV_area = population_std(area) / mean(area)
```

当面积样本数达到最低要求且 `CV_area` 超过阈值时触发验证。当前配置为：

| 类别 | 面积窗口 | 最少面积样本 | 面积变化阈值 | 最短持续时间 |
|---|---:|---:|---:|---:|
| fire | 20 | 2 | 0.05 | 0.0 s |
| smoke | 20 | 2 | 0.05 | 0.0 s |

额外设置至少 2 个样本，是为了避免单样本标准差为零时产生没有意义的判断。

### 6.4 两种算法对比

| 比较项 | TPT | AVT |
|---|---|---|
| 主要依据 | 命中次数、持续时间、丢失次数 | 检测框面积变化系数 |
| 适合场景 | 目标较稳定、希望规则直观的场景 | 火焰/烟雾轮廓持续变化的场景 |
| 优点 | 可解释、抗单帧误检、参数含义直观 | 触发快，能利用非刚性目标的面积变化 |
| 风险 | 轨迹碎片会使持续时间重新累计 | 摄像头抖动、框抖动也可能造成面积变化 |
| 延迟倾向 | 由最短持续时间决定，通常更稳但更慢 | 最少 2 个样本即可触发，通常更快 |
| 当前项目结论 | 保留作为稳健对照和可切换方案 | 当前 49 个视频组合测试更优，作为默认值 |

当前推荐生产候选配置使用 AVT，但不能据此断言 AVT 在所有场景都优于 TPT。室内固定摄像头、持续性明显但面积变化小的目标，TPT 可能更稳定；存在云台运动或强烈画面缩放时，AVT 必须额外防止由相机运动产生的伪面积变化。

### 6.5 门控的职责边界

TPT 和 AVT 都只决定是否启动第二级验证，不判断最终真假。门控阈值过严会造成真实事件无法进入大模型，阈值过松会增加推理负载。因此应评价两项指标：

- 真实事件通过门控的召回率；
- 每小时产生的验证请求数量。

仅比较门控后的框是否“看起来更干净”是不够的。

## 7. 视频缓冲、片段与 ROI 构建

### 7.1 环形缓冲

系统始终维护最近 `3.2` 秒、目标 `10 FPS`、共 `32` 帧的时间戳感知环形缓冲。缓冲写入独立于 YOLO 推理，因此正常状态即使 YOLO 只运行 5 FPS，也能保留足够的二级模型输入。

门控一旦通过，第一段验证直接使用触发前已经存在的 3.2 秒片段，不额外等待未来 3.2 秒。这可以显著降低首次验证延迟，并让模型看到火焰或烟雾出现前后的变化。

### 7.2 固定 ROI

系统根据 32 个时间点的轨迹框构造统一 ROI：

1. 对缺失时间点的框和置信度按轨迹时间插值；
2. 求整段轨迹框的并集；
3. 以并集中心生成固定正方形；
4. 正方形边长按 `roi_scale=1.5` 向外扩展；
5. 超出画面的部分采用反射填充；
6. 每帧裁剪并缩放为 `224×224`。

整段使用同一个 ROI，避免逐帧裁剪框的缩放抖动被模型误认为真实火焰闪烁。1.5 倍扩展还保留目标周围环境，便于区分火焰与灯具、烟雾与天空或蒸汽源。

### 7.3 片段质量检查

每个验证请求记录：

```text
actual_frame_count
requested_frame_count
effective_fps
max_frame_gap
frequency_valid
reasons
```

出现以下任一情况时，频域分支标记为无效：

- 实际有效帧少于 26；
- 有效帧率低于 8 FPS；
- 最大真实帧间隔超过 0.25 秒。

构建固定长度张量时可能为 RGB 分支选择最近帧，但系统通过有效帧索引检查阻止重复帧伪造频谱。频域无效时不计算虚假频率结论，而是显式退化为 RGB 时序与轨迹统计判断。

## 8. 第二级 MViT-v2-S 视频验证模型

### 8.1 模型选型

生产主模型选择 TorchVision 的 **MViT-v2-S**。它是多尺度视频 Transformer，约 34.5M 参数，标准输入为 `16×224×224`，移除分类头后输出 768 维视频特征。

选择它的主要原因是：

- 直接对时空 token 建模，比逐帧图片分类更适合火焰闪烁、烟雾扩散等动态现象；
- 多尺度结构能够同时利用局部纹理和较长时间变化；
- TorchVision 提供实现和 Kinetics-400 预训练权重，易于集成和部署；
- 在 RTX 3090 上单片段推理可远低于 1 秒目标，能够支持触发式在线验证；
- 相比将 VideoMAE 官方仓库作为生产依赖，TorchVision 的工程集成和许可证管理更清晰。

VideoMAE-S 仍可作为论文对照，但其官方仓库采用 CC BY-NC 许可，不作为当前生产依赖。正式商用前仍必须审核 TorchVision 代码、预训练权重、Kinetics-400 训练数据以及本项目训练数据的授权，不能只根据代码仓库许可证做结论。

### 8.2 RGB 时序分支

从完整 32 帧中均匀抽取 16 帧，形成：

```text
[C, T, H, W] = [3, 16, 224, 224]
```

所有帧使用一致的空间裁剪和增强。输入归一化后进入 MViT-v2-S，输出 768 维 RGB 时序特征。

该分支主要学习：

- 火焰边缘的非刚性变化和闪烁；
- 烟雾的扩散、透明度和纹理变化；
- 候选与周围环境的空间关系；
- 连续多帧中的形态一致性。

### 8.3 时间频域分支

频域分支使用全部 32 帧构造三条时间序列：

1. ROI 亮度帧差均值；
2. 检测框面积占整帧面积的比例；
3. YOLO 置信度。

每条序列先进行标准化，再乘 Hann 窗并执行实数快速傅里叶变换：

```text
x_norm = (x - mean(x)) / (std(x) + ε)
X = rFFT(x_norm × Hann)
feature = log(1 + |X|²)
```

32 个时间点的 `rFFT` 产生 17 个频率分量，三条序列共 `3×17=51` 维特征。51 维频谱与 1 维 `frequency_valid` 标志一起进入两层 MLP，编码为 128 维。

该分支不是把二维图像转换到空间频域，而是分析亮度变化、面积变化和检测置信度随时间的频率结构，用于区分持续但静止的灯光、周期性闪烁、自然火焰变化、缓慢扩散烟雾等现象。

当 `frequency_valid=false` 时，频域特征被置零并通过硬掩码从融合结果中移除。

### 8.4 轨迹统计分支

轨迹分支输入 6 个可解释统计量：

```text
1. 归一化面积增长率
2. 面积变异系数
3. 有效检测的平均置信度
4. 有效检测的最大置信度
5. 命中率
6. 丢帧率
```

其中极端面积增长率和变异系数会裁剪到合理范围，防止异常框主导结果。6 维输入经 MLP 编码为 32 维轨迹特征。

### 8.5 类别嵌入与融合

YOLO 已经提供候选类别，因此验证器不重新执行 fire/smoke 互斥分类。候选类别被编码为 16 维嵌入，与三条分支拼接：

```text
768 维 MViT RGB 特征
+ 128 维频域特征
+ 32 维轨迹特征
+ 16 维类别嵌入
= 944 维融合输入
```

融合输入经过 LayerNorm、256 维线性层、GELU 和 Dropout。模型设置 fire、smoke 两个独立二分类头，只选择与 YOLO 候选类别对应的头输出 logit，经 Sigmoid 得到：

```text
p_real = P(该 YOLO 候选是真实的 fire/smoke)
```

最终类别仍沿用 YOLO，避免验证器在“火焰还是烟雾”之间重新竞争。

### 8.6 可用模型模式

同一训练框架支持以下模式，便于消融实验：

| 模式 | RGB/MViT | rFFT | 轨迹 | 用途 |
|---|---:|---:|---:|---|
| `fusion` | 是 | 是 | 是 | 当前完整生产候选模型 |
| `rgb` | 是 | 否 | 否 | 验证频域和轨迹是否真正带来收益 |
| `frequency` | 否 | 是 | 是 | 验证非视觉分支的独立能力 |

骨干还支持 `r3d_18`，用于确认 Transformer 相对传统 3D CNN 是否有实际收益。

## 9. 多窗口验证、会话重关联与报警

### 9.1 验证请求和结果

验证请求的逻辑字段为：

```python
request = {
    "event_id": "camera_001:12",
    "camera_id": "camera_001",
    "track_id": 12,
    "candidate_class": "fire",
    "frames": 32,
    "timestamps": [],
    "bboxes": [],
    "confidences": [],
    "observed": [],
    "quality": {},
}
```

模型结果包含：

```python
result = {
    "event_id": "camera_001:12",
    "candidate_class": "fire",
    "p_real": 0.97,
    "clip_positive": True,
    "threshold": 0.80,
    "model_version": "mvit-v2-s-verifier-v1",
    "quality": {},
    "inference_ms": 110.0,
}
```

训练检查点中的分类别阈值优先于 `config/verifier.yaml` 的占位阈值。

### 9.2 2/3 窗口投票

验证状态下每 0.5 秒形成一个滑动窗口。系统保存最近 3 个窗口的布尔结果：

```text
p_real ≥ 当前类别阈值 → 阳性
最近 3 个窗口至少 2 个阳性 → 确认报警
```

该设计允许一个窗口受遮挡、模糊或跟踪误差影响，同时避免单个高分窗口立即报警。验证会话最长持续 10 秒，防止长期占用推理资源。

### 9.3 会话重关联

轨迹暂时丢失时，验证会话不会立即关闭。系统保留最近轨迹框和已有窗口投票，在 1.25 秒宽限期内：

- 原轨迹恢复时继续同一事件；
- 同类别新轨迹与旧 ROI 空间接近时合并；
- 并行产生的短轨迹不重复建立独立完整会话。

这使报警确认依赖真实空间事件，而不是完全依赖不稳定的 `track_id`。

### 9.4 报警冷却与日志类型

确认报警后，系统同时使用：

- 同区域冷却 `alarm_cooldown_seconds=10.0`；
- 同摄像头同类别全局冷却 `global_alarm_cooldown_seconds=10.0`。

当前输出的主要日志类型为：

| `message_type` | 含义 |
|---|---|
| 未设置 | 原始门控触发事件 |
| `verification` | 一个二级模型窗口的结果 |
| `alarm` | 已满足 2/3 投票的确认报警 |
| `verification_suppressed` | 因冷却或重复事件而取消的验证 |
| `verification_error` | 片段构建或模型推理失败 |

被冷却抑制的事件使用 `reason=alarm_cooldown`，便于区分“模型判断为阴性”和“同一报警被去重”。

## 10. 系统状态与完整处理流程

### 10.1 状态定义

从工程逻辑上，单摄像头事件可表示为以下状态：

```text
NORMAL → CANDIDATE → VERIFYING → ALARM → COOLDOWN
   ↑          │           │          │        │
   └──────────┴───────────┴──────────┴────────┘

任意状态遇到视频时间戳异常、断流或模型异常时记录 FAULT/ERROR
```

当前代码主要通过轨迹、验证会话和冷却记录实现这些状态，而不是依赖单个全局枚举，因此能够同时处理同一摄像头中的多个候选。

### 10.2 NORMAL

```text
1. 读取视频帧并校验时间戳；
2. 按 10 FPS 写入环形缓冲；
3. 按 5 FPS 执行 YOLO；
4. 没有候选时向跟踪器提交有效空结果；
5. 有候选时执行类别阈值和忽略区过滤；
6. 更新轨迹并执行当前 TPT/AVT 门控。
```

### 10.3 CANDIDATE

```text
1. 记录首次出现时间、框、类别和置信度；
2. 与当前活动轨迹进行关联；
3. TPT 累计命中和持续时间，或 AVT 累计面积变化；
4. 未通过时继续观察；
5. 轨迹超时则删除；
6. 通过门控则创建验证事件。
```

### 10.4 VERIFYING

```text
1. YOLO 临时提高到 10 FPS；
2. 使用当前缓冲立即构建第一个 3.2 秒窗口；
3. 固定轨迹并集 ROI 并生成三分支输入；
4. 根据片段质量决定是否启用频域分支；
5. 调用 MViT-v2-S 验证器；
6. 每 0.5 秒重复构建新窗口；
7. 维护最近 3 个窗口投票；
8. 达到 2 个阳性则进入 ALARM；
9. 超时、轨迹消失且未确认时关闭会话。
```

### 10.5 ALARM 与 COOLDOWN

```text
1. 输出唯一 event_id、类别、p_real、时间戳、模型版本和质量信息；
2. 上层系统据此保存事件视频并发送报警；
3. 记录同区域和同摄像头同类别冷却；
4. 冷却期内的新碎片轨迹输出 suppressed，不重复报警；
5. 冷却结束后若目标仍存在，可以建立新的事件。
```

冷却并不等同于火灾已经解除。生产系统还应在 `alarm` 之上增加报警锁存、人工确认和持续阴性恢复策略，例如连续 8 秒无有效候选后才将业务报警状态转为恢复。

## 11. 数据生成与训练方案

### 11.1 为什么必须从前级流水线采样

第二级模型的训练样本不能使用随机裁剪的普通背景，而必须由真实 `YOLO + AVT/TPT` 链路产生。否则训练集中的负样本过于简单，模型上线后面对 YOLO 真正容易误检的灯光、反光、蒸汽和云雾时会失效。

候选采集命令：

```bash
python run_temporal.py \
  --source input.mp4 \
  --candidate-dir verifier_candidates \
  --device 0
```

输出为 `.npz` 片段和 `manifest.jsonl`。每条记录至少包含 `source_id`、候选类别、标签、划分和许可信息。

### 11.2 标签定义

对于候选类别 `fire`：

- `label=1`：该候选 ROI 中存在真实火焰；
- `label=0`：YOLO 认为是火焰，但实际是灯光、夕阳、焊接、反光等误报。

对于候选类别 `smoke`：

- `label=1`：该候选 ROI 中存在真实烟雾；
- `label=0`：实际是蒸汽、云、雾、灰尘或背景纹理。

当前数据只有视频级弱标签。为避免把“火焰正视频中误检出的烟雾框”错误标为烟雾正样本，本次生成时跳过了 83 个跨类别正候选。这种保守规则能减少明显标签污染，但不能代替逐片段人工复核。

### 11.3 数据划分

必须按原始视频或摄像头来源分组划分。来自同一 `source_id` 的重叠片段只能出现在 train、val、test 中的一个集合。

本次使用：

```text
dataset/fire_videos.1406   ：27 个 AVI
dataset/smoke_videos.1407  ：22 个 AVI
总计                        ：49 个视频
```

前级流水线共生成 1021 个候选窗口，保守弱标签筛选后使用 711 个：

| 划分 | 来源数 | fire 负/正 | smoke 负/正 | 总样本 |
|---|---:|---:|---:|---:|
| train | 16 | 10 / 137 | 53 / 199 | 399 |
| val | 8 | 3 / 72 | 8 / 95 | 178 |
| test | 7 | 1 / 70 | 8 / 55 | 134 |

这里最明显的问题是 fire 负样本严重不足，test 中只有 1 个 fire 负片段。因此当前 fire 测试结果不能证明模型已经具备可靠的火焰误报抑制能力。

另外，49 个视频此前已参与前级参数选择，现在又用于二级模型训练和域内测试，不能再作为最终独立验收集。

### 11.4 许可状态

本次数据划分摘要中的许可状态是：

```text
unverified
```

同时，当前原始 `verifier_candidates/manifest.jsonl` 中候选仍保留 `split=unlabeled`、`label=null` 和 `license=null`。这表示数据目前只适合作为本地研究实验，现有划分摘要和实验权重不能据此用于商业交付。正式训练归档前必须生成并保存经过人工确认的有标签清单，为每个来源记录明确授权、原始视频 ID 和用途限制，并移除许可不明或仅限非商业使用的数据。

### 11.5 两阶段训练

训练采用加权 `BCEWithLogitsLoss` 处理正负样本不均衡，分两阶段进行：

1. **分类头阶段**：冻结 MViT 骨干，仅训练频域编码器、轨迹编码器、融合层和 fire/smoke 真实性头；
2. **微调阶段**：只解冻 MViT 最后两个 block 和归一化层，使用更小学习率微调并早停。

当前模型使用 TorchVision Kinetics-400 预训练权重。本次训练执行了 5 个 head epoch 和最多 10 个 finetune epoch，最佳微调检查点出现在第 8 个 epoch。

训练增强必须对整段视频保持一致。当前实现包括整段一致的水平翻转、亮度和对比度变化；不能随机打乱帧顺序，也不随意进行时间反转。

### 11.6 分类别阈值校准

fire 和 smoke 分别在验证集上校准，不直接使用固定 `0.5`。当前检查点阈值为：

```text
fire  = 0.8002423644
smoke = 0.7930642962
```

运行时加载权重后自动使用检查点阈值。更换数据域或重新训练后必须重新校准，不能长期固化这两个数值。

## 12. 当前实验结果及正确解读

### 12.1 模型文件

当前训练权重：

```text
路径：weights/mvit_v2_s_fire_smoke.pt
大小：138258411 bytes（约 132 MiB）
SHA-256：6dee76c6f38d8320294abb458d36bd66e9efd7ad70a73beba2232f55ec9cbaac
```

### 12.2 片段级结果

在当前域内 test 划分的 134 个候选片段上：

| 指标 | 总体 | fire | smoke |
|---|---:|---:|---:|
| TP | 125 | 70 | 55 |
| FN | 0 | 0 | 0 |
| FP | 1 | 0 | 1 |
| TN | 8 | 1 | 7 |
| Precision | 0.9921 | 1.0000 | 0.9821 |
| Recall | 1.0000 | 1.0000 | 1.0000 |
| F1 | 0.9960 | 1.0000 | 0.9910 |
| PR-AUC | 0.99994 | 1.0000 | 1.0000 |

这些数字说明模型已经正确贯通训练、校准和推理链路，但负样本只有 9 个，尤其 fire 负样本只有 1 个，因此不能把接近 1.0 的结果解释为生产环境准确率。

### 12.3 严格轨迹事件结果

早期按 `track_id` 严格分组的事件评估为：

```text
Precision = 1.0000
Recall    = 0.4737
平均报警延迟约 1.00 秒
```

片段模型得分很高但事件召回较低，主要原因不是 MViT 分类失败，而是轨迹碎片使 20 个正轨迹无法积累到 3 个窗口。这一结果直接暴露了“片段分类正确不等于完整系统报警正确”，也是本项目进一步解决轨迹碎片化的依据。

### 12.4 轨迹碎片化修复回归

加入运动预测、验证会话重关联和报警冷却后，在 5 个正来源与 2 个负来源的小规模在线回归中：

```text
TP=5，FN=0，FP=0，TN=2
代理 Precision=1.0，Recall=1.0
```

基准视频 `posVideo8.877.avi` 的门控事件由 6 个降到 5 个，验证窗口由 10 个降到 7 个；仍确认 2 次报警，并抑制 2 个重复事件。

这个回归证明修复方向有效，但样本量只有 7 个来源，且与训练域重叠，只能视为代码回归结果，不能视为系统最终性能。

### 12.5 推理性能

RTX 3090 上，MViT-v2-S 随机权重结构基准的 FP16 单片段纯模型推理约 16 ms；预热后的独立验证曾约 18 ms。当前完整在线链路在并发解码和 YOLO 运行条件下，单验证窗口平均约 111 ms。

应以在线端到端延迟为部署依据，因为真实延迟还包括：

- 视频解码与缓冲；
- ROI 裁剪和缩放；
- 特征构建；
- GPU 排队和数据传输；
- 0.5 秒滑动步长以及 2/3 投票等待。

现有结果满足“单窗口 1 秒内返回”的目标，但多摄像头容量仍需通过并发压测确定。

## 13. 评估与对照实验要求

### 13.1 模型级消融

必须在相同来源划分、相同候选和相同随机种子下完成：

1. R3D-18 基线；
2. MViT-v2-S 仅 RGB；
3. 仅频域与轨迹特征；
4. MViT-v2-S + 频域 + 轨迹完整融合；
5. 5 FPS 与 10 FPS 输入；
6. ROI 扩展比例，例如 1.0、1.25、1.5、2.0。

频域实验改变采样率时必须重新从源视频构造特征，不能简单抽取旧频谱张量，否则频率轴的物理含义不一致。

### 13.2 TPT/AVT 与置信度组合

前级调参应采用网格实验，并同时记录：

```text
temporal ∈ {tpt, avt}
fire_conf ∈ 候选集合
smoke_conf ∈ 候选集合
```

不能只按最终 Precision 选择阈值。建议先约束事件召回不低于目标值，再在满足召回的组合中选择每小时验证次数和误报最少的配置。

当前域内最优配置为 AVT、fire 0.60、smoke 0.20，已经写入 `config/temporal.yaml`。独立新数据到位后必须冻结搜索范围并重新验证，防止继续在同一批 49 个视频上过拟合参数。

### 13.3 核心指标

片段级指标：

- fire/smoke 分类别 Precision、Recall、F1、PR-AUC；
- 固定 95% Recall 下的 FPR；
- 分类别校准曲线和阈值稳定性。

门控级指标：

- TPT/AVT 真实事件通过率；
- 每小时验证请求数；
- 门控平均等待时间；
- 轨迹碎片数和平均轨迹长度。

系统级指标：

- 每小时、每摄像头误报警次数；
- 真实事件召回率；
- 从首次可见到 `alarm` 的平均和 P95 延迟；
- 同一事件重复报警率；
- 频域无效片段比例；
- GPU 显存、吞吐和多路视频排队延迟；
- 断流与恢复处理结果。

### 13.4 最终验收数据

最终验收必须增加一批满足以下条件的视频：

- 未参与 YOLO、TPT、AVT、阈值和 MViT 的任何训练或调参；
- 按摄像头或原始视频来源分组；
- 包含足够的 fire 和 smoke 困难负样本；
- 覆盖昼夜、室内外、不同分辨率、雨雾、强光和摄像头抖动；
- 标签经过人工逐事件复核并具有明确授权。

融合模型只有在相对“MViT 仅 RGB”显著降低困难负样本误报，同时不降低 fire/smoke 事件召回时，才能证明频域分支确实有价值。

## 15. 与 Fire-Detection 参考项目的关系

参考项目的基本链路是：

```text
YOLOv5 → AVT 或 TPT 时间分析 → 过滤后的检测结果
```

本项目借鉴其 TPT 持续性和 AVT 面积变化思想，但没有直接把原实现当作完整系统。本项目进一步增加：

- 与当前 Ultralytics YOLO 输出适配的统一后处理；
- 按摄像头、类别和轨迹隔离的状态；
- 可切换 TPT/AVT 的统一事件接口；
- 轨迹运动预测和失配容忍；
- 触发前环形视频缓冲；
- MViT-v2-S、rFFT 和轨迹统计融合验证；
- 2/3 滑动窗口投票；
- 轨迹碎片后的会话重关联和报警去重；
- 候选数据生成、训练和评估工具。

因此，TPT 和 AVT 在本系统中是“第二级验证的触发门控”，不是最终检测器，也不是大模型本身。

## 16. 系统优势

### 16.1 兼顾召回和误报控制

YOLO 使用低内部阈值保存候选，分类别阈值和时序门控控制调用，大模型再处理困难误报。相比单模型直接报警，更容易在召回率和误报率之间找到可解释的平衡。

### 16.2 同时利用三种证据

系统不是只增加一个更大的图像分类器，而是同时利用：

- MViT 的外观与时空关系；
- rFFT 的时间频率结构；
- 检测框面积、置信度和命中率的轨迹统计。

三类证据具有互补性，适合处理火焰和烟雾的非刚性动态特征。

### 16.3 计算资源按事件分配

正常状态主要运行 YOLO，只有门控通过才运行 MViT。触发前片段已经在缓冲中，因此无需让大模型连续处理全部视频，也无需等待完整未来片段。

### 16.4 可解释和可调试

一次报警可以追溯到：

```text
YOLO 类别和置信度
→ 跟踪匹配与轨迹历史
→ TPT/AVT 通过原因
→ 片段质量和 p_real
→ 最近三个窗口投票
→ 冷却和去重结果
```

这比只输出一个最终概率更适合排查现场误报。

### 16.5 模块可替换

TPT 和 AVT 可切换；MViT 可替换为 R3D-18 做基线；三分支可以独立消融。系统边界清晰，便于后续更换 YOLO 权重、加入新门控或部署不同规格的视频骨干。

## 17. 风险、局限与改进方向

### 17.1 前级漏检传播

如果 YOLO 完全没有产生候选，后续门控和大模型都不会运行。解决方向包括：

- 在独立新数据上优先保证 YOLO 事件召回；
- 高风险区域周期性提高 YOLO 帧率；
- 将运动、亮度异常或独立烟雾分割作为补充触发器；
- 对不同摄像头校准 fire/smoke 候选阈值。

### 17.2 门控延迟或过早触发

TPT 过严会延迟或漏掉短时真火，AVT 过松会被检测框抖动触发。必须同时对比门控召回、调用次数和报警延迟，而不是只选择触发最少的参数。

### 17.3 轨迹碎片仍可能发生

当前几何与运动预测适合单摄像头短时关联，但严重遮挡、大范围快速移动、云台转动和多个相邻火源仍可能发生错误合并或拆分。后续可评估 ByteTrack、Kalman Filter 或带外观特征的跟踪器，但必须用系统级事件指标证明收益。

### 17.4 频率特征受采样质量影响

rFFT 对真实时间间隔敏感。低帧率、变帧率、网络抖动和重复帧都会改变频谱。当前质量掩码只能阻止明显无效输入，生产阶段还需要统计每个摄像头的频域有效率，并对长期无效的源进行运维告警。

### 17.5 数据量与负样本不足

当前 711 个弱标签片段远不足以覆盖真实场景，尤其缺少 fire 困难负样本。下一批数据应优先收集：

- 红色或橙色灯光、车辆尾灯和警示灯；
- 夕阳、焊接、切割火花和强反光；
- 蒸汽、云、雾、灰尘、雨雪；
- 屏幕中的火焰视频；
- 夜间噪声、压缩伪影和摄像头抖动；
- 小火、远距离烟雾和被遮挡目标。

### 17.6 域内高指标不可外推

现有训练、验证和测试都来自同一批 49 个视频，且负样本很少。当前结果的价值是验证架构可运行并发现轨迹碎片问题，不是证明现实误报率已经达到部署要求。

### 17.7 报警工程可靠性

程序输出 `alarm` 不代表报警链路已经可靠。生产系统还需实现：

- 事件 ID 幂等；
- 消息失败重试和持久化队列；
- 报警视频保存和磁盘配额；
- 服务重启后的状态恢复；
- GPU 不可用时的降级策略；
- 摄像头断流、时间不同步和质量告警；
- 报警解除、人工确认和审计记录。

### 17.8 许可证风险

数据集许可目前未核实，不能用于商业结论。VideoMAE 官方实现也有非商业限制。上线前必须完成代码、权重、预训练数据和所有训练视频的逐项许可审查。

## 18. 后续实施顺序

建议按以下优先级继续推进：

1. 人工复核现有 711 个候选片段，清理弱标签错误；

10. 冻结模型版本、阈值和配置，进行现场试运行。

## 19. 最终推荐方案

当前项目推荐的默认链路为：

```text
视频缓冲 10 FPS
    ↓
YOLO 正常 5 FPS / 验证期 10 FPS
    ↓
Ultralytics 内置 NMS
    ↓
fire conf 0.60 / smoke conf 0.20
    ↓
运动辅助分类目标跟踪
    ↓
AVT 默认门控（TPT 可切换）
    ↓
3.2 秒、32 帧、1.5 倍固定 ROI
    ↓
MViT-v2-S RGB + rFFT + 轨迹统计融合
    ↓
fire/smoke 分类别 p_real 阈值
    ↓
最近 3 个窗口至少 2 个阳性
    ↓
会话重关联 + 10 秒报警冷却
    ↓
最终 alarm 事件
```

这个架构已经具备从视频输入、候选检测、时序门控、二级验证到报警事件的完整主干。当前下一阶段的重点不再是继续堆叠模型，而是补足有授权的困难负样本、建立真正独立的测试集，并用事件级误报率、召回率和报警延迟证明系统在新场景中的有效性。
